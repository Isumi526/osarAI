# 技術的な意思決定の記録

このプロジェクトで行った判断と、その理由を記録する。

「なぜそうしたか」を後から説明できる状態を保つことが目的。

## 記録のフォーマット

### [日付] 決定内容

- **背景**: なぜこの判断が必要になったか
- **選択肢**: 検討した案
- **決定**: 採用した案
- **理由**: なぜそれを選んだか
- **却下した案と理由**:
- **見直しの条件**: どうなったら再検討するか

---

### [2026-08-13] SPEC.md の前提を「移行」から「新規構築」へ改訂し、Phase 0 を新設する

- **背景**: SPEC.md 初版は「AI診断は 13問・12カテゴリのルールベースで実装済み」を前提に
  書かれていたが、リポジトリ横断調査（全ブランチ・全コミット・作業ツリー）で該当実装が
  1件も存在しないことが判明した（判定 C）。移植元が無いため `diagnosis/rules.py` の
  中身を決める工程がどこにも無く、かつカテゴリ定義に依存する Phase 2（評価設計）が
  着手不能になる。
- **選択肢**:
  - (a) SPEC.md を原文のまま保持し、Phase 1-B で実装者が適当にカテゴリを決める
  - (b) SPEC.md の前提を改訂し、事業責任者が仕様を確定する Phase 0 を新設する
  - (c) 診断機能をやめ、既存のおさらい対話に RAG を適用する形へスコープ変更する
- **決定**: (b)。SPEC.md の 0.1 / 0.2 / 0.3 / 2.1 / 2.3 / 3.2 / 7 を改訂し、
  §1 と §2 の間に「Phase 0：診断ロジックの新規設計」を新設。
- **理由**: カテゴリ定義は事業仕様の判断であり実装者が独断で決めるべきではない。
  また Phase 2 が最重要と定義されている以上、その前提となるカテゴリ定義を
  最初に確定させないと優先度の宣言と実際の依存関係が矛盾する。
- **却下した案と理由**:
  - (a) 事業仕様を実装者が決めることになる。誤った前提のまま書かれた仕様書が
    後続セッションの正本として参照され続けるリスクもある。
  - (c) 副次目的（RAG の設計・実装・評価の実務経験）は満たせるが、
    「ルールベースの骨格 + RAG の肉付け」という中核の設計思想が検証できなくなる。
- **見直しの条件**: Phase 0 手順3 で事業責任者が「診断機能そのものを作らない」と
  判断した場合は (c) を再検討する。

### [2026-08-13] プロジェクトの位置づけを「リスクを取る変更」から「今あるリスクを管理下に置く変更」へ改める

- **背景**: SPEC.md 初版 0.2 は「法務リスクは現状ルールベースで回避されている」と
  記していたが、事実ではなかった。既存の おさらい対話 / AI戦略相談 / アポ戦略cron は
  すでに LLM が自由生成した文章をユーザーへ届けており、出典グラウンディング・
  禁止表現チェック・免責表示のいずれも実装されていない。
- **選択肢**:
  - (a) 事実誤認の記述のみ訂正して先へ進む
  - (b) 位置づけ自体を改め、既存機能への横展開を副次目的に加える
- **決定**: (b)。0.2 に位置づけの説明を追記し、0.3 副次目的に
  「既存の LLM 自由生成機能への出典グラウンディングとガードレールの後付け適用」を追加。
- **理由**: 診断機能だけをガードレールで守っても、同じアプリ内の他の LLM 経路が
  無防備ならプロダクト全体のリスクは下がらない。とくに保険代理店 agent network
  （150〜250名規模）への展開が予定されており、金融領域は表現規制が厳しい。
  ベータ5名時点とはリスク水準が異なる。
- **却下した案と理由**: (a) 訂正だけでは、本プロジェクトで作るガードレールが
  既存機能へ展開されないまま終わる。技術的負債の所在を仕様書に明記しないと忘れられる。
- **見直しの条件**: 既存機能のリスク調査の結果、応急処置が本プロジェクトと独立に
  先行実施された場合は、副次目的の記述を実績に合わせて更新する。

### [2026-08-13] Phase 0 の節を「番号なし」で §1 と §2 の間に置く

- **背景**: Phase 0 を SPEC.md のどこに置くか。素直に `## 2.` として挿入すると
  以降の全節（現 2〜7）を繰り下げる必要がある。
- **選択肢**: (a) 全節を繰り下げる (b) 番号なしの節として §1 と §2 の間に置く
  (c) 文書末尾に追記する
- **決定**: (b)。見出しは `## Phase 0：診断ロジックの新規設計【2026-08-13 新設・§2 の前提工程】`。
- **理由**: 「付録A の 2.1 の構成」「2.3 の DDL」のように、節番号が
  他ドキュメント・過去の指示から参照されている。繰り下げると既存の参照がすべて壊れる。
- **却下した案と理由**: (a) 参照崩れ。(c) 実行順序が Phase 1 より前なのに
  文書末尾にあると読み手が順序を誤認する。
- **見直しの条件**: 次に SPEC.md を大きく改訂する機会があれば、
  そのタイミングで全体の節番号を振り直す。

### [2026-08-13] `.gitignore` に terraform 系を追加。ただし `.terraform.lock.hcl` は追跡対象のまま残す

- **背景**: Phase 3 で Terraform を使う。指示は `*.tfstate` / `*.tfvars` の追加だった。
- **決定**: `*.tfstate` / `*.tfstate.*` / `*.tfvars` / `.terraform/` を追加。
  `.terraform.lock.hcl` は **ignore しない**。
- **理由**: `*.tfstate.*`（state のバックアップ）は tfstate 本体と同じ秘密漏洩リスクを持つため
  合わせて除外。一方 `.terraform.lock.hcl` はプロバイダのバージョンとハッシュを固定する
  ロックファイルで、コミットするのが正。第三者が同じ構成を再現できること（Phase 3 完了条件）に
  直結する。
- **却下した案と理由**: ロックファイルも ignore する案 — プロバイダ版が実行環境ごとに
  変わり、再現性が失われる。
- **見直しの条件**: なし。
